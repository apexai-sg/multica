本地 Docker Fleet 是可选的组件，它把执行节点作为 Docker 容器管理，并与 API 共用当前 checkout 的 PostgreSQL 数据库。它复用现有的守护进程、运行时、任务队列和回传协议。本页说明本地 API 接入、可选托管环境组件、Aurora 受管智能体、约束删除行为的安全规则、验证门，以及该方案不提供的能力。

## 本地 API 接入

通过两个变量启用本地 Fleet 接入：

- `MULTICA_LOCAL_FLEET_URL` — API 调用的 Fleet URL。
- `MULTICA_LOCAL_FLEET_SECRET_FILE` — 保存 Fleet 服务密钥的私有密钥文件路径。

本地 URL **与 `MULTICA_CLOUD_URL` 互斥**。两者同时设置会在启动时失败，并报 `local Fleet and SaaS Cloud are mutually exclusive`。本地模式不会启用 Cloud Billing、entitlement 策略或严格的预购席位容量。

URL 在启动时会经过校验：

- scheme 必须是 `http` 或 `https`。
- host 必须是 `localhost` 或回环 IP 地址。
- 不允许 userinfo、query 和 fragment，path 必须为空或为 `/`。

密钥文件在启动时会经过校验：

- 绝对路径指向普通文件，不能是符号链接，并会与打开的 descriptor 再核对一次。
- 所有者可读的私有权限：无 group 或 other 位，且设置所有者读位（`0600` 或 `0400`）。
- 去除首尾空白后至少 32 字节、至多 65536 字节，且不含换行。

本地模式创建 Fleet token 校验器时不配置 Redis 客户端，这会**禁用正向校验缓存**。每个节点（`mcn_`）token 都会重新向本地 Fleet 校验，而不是命中缓存。内部操作端点用常量时间比较校验复制的服务密钥，并在 SQL 中重新核对确切的节点凭据和容器身份。

## 可选托管环境组件

托管环境默认仍为 `api,web`。需要显式选择 Fleet 组件：

```sh
make up C=api,web,fleet
make status
make down
```

- `make down` 停止进程并保留数据。
- `make destroy` 需要显式确认，并删除环境及其数据。
- 默认的 `make up` 仍然只启动 `api,web`。

该组件需要两个私有输入，两者都是绝对私有路径，而不是凭据值：

- `MULTICA_FLEET_INPUT` — 私有描述文件。
- `MULTICA_FLEET_OPERATOR` — 私有、仅所有者可执行的 Fleet 环境 operator，由 `server/cmd/fleet-env` 构建。

`scripts/fleet-env.sh` 负责物理来源，提供这些动作：`prepare`、`up`、`status`、`quiesce`、`down` 和 `destroy`。

`prepare` 会校验描述文件，验证所选 Docker Engine、PostgreSQL 容器、其 compose 标签、其发布的回环端口、其网络，以及容器内可见的 Docker socket 组，验证两个镜像都以摘要固定，拒绝占用已分配端口的无关监听者，在 `19000`–`20999` 范围内分配回环 Fleet 端口，持久化注册表身份，迁移现有 checkout 数据库，然后调用 operator 准备 profile。这里没有第二个 PostgreSQL 实例，也不会公开重新绑定。

注册表持久化托管命名空间、Fleet ID、已分配端口和关闭（operation）密钥。之后的 `status`、`quiesce`、`down` 和 `destroy` 复用这些已保存的路径，因此同一 checkout 在重启后保持稳定身份，不同 worktree 之间保持隔离。

网络被刻意收窄：

- Fleet 只加入已验证的共享 PostgreSQL Docker 网络和自己的节点网络。
- 普通节点加入节点网络；Aurora 节点加入自己可直接出站的每节点 bridge 网络。两者都不加入 PostgreSQL 网络。
- 只发布 Fleet 端口，且只绑定回环。

镜像必须使用以摘要固定的 `repository@sha256:...` 引用。`docker-compose.fleet.yml` 不发送 checkout 构建上下文，compose 创建使用 `--no-build`。

version 1 描述文件声明这些字段：`version`、`database_name`、`database_lifecycle`、`context`、`engine_id`、`pg_container_id`、`pg_network_id`、`pg_alias`、`pg_port`、`pg_host_port`、`socket_path`、`uid`、`gid`、`socket_gid`、`node_image`、`fleet_image`、`api_url`、`profiles_file`、`service_key_file` 和 `aurora`。它必须指定确切的已注册数据库（`database_name` 必须等于 checkout 数据库），并且只有在单独的物理所有权预检之后才能声明 `database_lifecycle=exclusive-managed`。注册表成员身份不是所有权证明；任何托管的数据库使用前都要核实当前数据库身份。

凭据 profile 使用严格的私有映射：

```json
{"version": 1, "owners": {"<canonical-nonzero-uuid>": "<absolute-private-path>"}}
```

owner 的值为空字符串表示禁用该 profile。凭据文件必须是普通、非符号链接的 `0600` 文件，由显式指定的非 root UID 拥有，其目录必须是 `0700`。`api_url` 是获准的 `host.docker.internal` API URL，会原样保留。

## Aurora 受管智能体

同一个 Fleet 可以运行 Aurora 的受管 skill 执行，而不只是默认的 Claude-only 节点。只有三个输入同时存在时，服务器才会构造 Aurora 的 fleet 客户端：`MULTICA_LOCAL_FLEET_URL`、`MULTICA_LOCAL_FLEET_SECRET_FILE`，以及指向 descriptor `image` 的、以摘要固定的 `AURORA_RUNTIME_IMAGE`。三者缺一时，`POST /api/aurora/generations` 仍在预留任何积分之前以 `aurora_runtime_unavailable` 失败关闭；catalog 和作品库端点不受影响。

Fleet 配置的 `aurora` 块用于选择受管智能体 profile（见 `fleet-config.example.json`）。配置由管理员提供；`claude_env` 可含凭据：

- `server_url` — 受管守护进程注册所针对的、容器可达的 Multica API origin。
- `anthropic_base_url` 和 `anthropic_model` — 可选的受管 Claude 端点覆盖；base URL 可带可选路径前缀（如 `/api/plan`），为空时保留供应商默认值。
- `claude_env` — 传给受管子进程的额外节点变量映射（可选），其中包含下述两个供应商凭据。
- `readonly_rootfs` — 必须显式为 `true`。

节点使用 `docker/runtime/Dockerfile`、`fleet-node run` 与 `/usr/local/bin/claude`。每节点自有的 bridge 网络支持直接出站，不再使用代理、供应商允许列表或 IP pin。

升级既有 Fleet 配置：`egress_hosts`、`egress_pins`、`uplink_network`、`proxy_image`、`seccomp_profile`、`apparmor_profile` 与 `provider_secret_files` 已删除。加载器会拒绝未知键，仍携带这些键的配置会让 Fleet 启动失败；请删除它们，并把供应商凭据保留在 `claude_env`。

`claude_env` 接受固定允许列表中的模型选择与工具路由变量：
`ANTHROPIC_DEFAULT_{FABLE,HAIKU,OPUS,SONNET}_MODEL` 及其 `_NAME` 变体、
`CLAUDE_CODE_SUBAGENT_MODEL`、`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`、
`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`、`ENABLE_TOOL_SEARCH` 和
`API_TIMEOUT_MS`（模型值可以使用带方括号后缀的形式，例如
`glm-5.3-flash[1M]`），外加且仅加两个供应商凭据：
`ANTHROPIC_API_KEY` 与 `VOLC_ASR_API_KEY`。前者是 Ark Agent Plan 的 key：
ARK 兼容 Anthropic Messages 协议，因此图片、视频与文字 skill 复用它，并把
`anthropic_base_url` 指向 ARK 端点。后者是火山语音的 key，也是唯一不兼容该协议的
供应商。除此之外，任何名称包含 API key、auth token、token、secret 或 password 的键
都会在配置加载时被拒绝，每个值都有长度上限并会检查空白与控制字符。

这两个凭据以值的形式出现在节点容器环境里，容器内任何进程都能读到，
`docker inspect` 也能看到；这是本方向接受的形态。它们必须在部署时由权限为
`0600` 的 Fleet 配置提供，绝不能进入镜像、SQL、日志或 Git。

受管节点以固定的 `fleet-node run` entrypoint 启动，并 `exec` 为 `multica daemon start --managed`。它的一次性注册密钥（`mse_`）写入节点只读 secrets 卷的 `/secrets/aurora-enrollment`；SQL 只存哈希，Fleet 只在进程内交接表中持有明文。沙箱以非 root（`10001:10001`）运行在只读根文件系统上，使用 `cap_drop: ALL` 与 `no-new-privileges`，并且只加入自己可直接出站的每节点网络。AppArmor 与自定义 seccomp 都不再使用：节点按 Docker 默认安全设置运行。供应商凭据是容器环境里的值，不再是挂载文件。

Aurora 使用普通智能体的 shell、供应商 CLI 与 Multica CLI，由技能文档驱动。模型写入 `.multica/aurora-artifacts.v1.json`；守护进程独立校验路径、文件类型与链接数、大小、MIME 和 SHA-256。供应商调用记录仅用于记账，不再有防重复计费的强制力。

目录里的每个条目都带可执行步骤：`server/internal/aurora/experts/` 下 24 个 SkillHub 专家，每个是一份 brief 加 6 个子技能，运行时可从 `.claude/skills/` 逐个读取（见 `AGENTS.md`）。原来的 16 个手写技能及其 Seedream/Seedance/ASR 路由已退役，因此没有专家会发起 provider run。旧源码可从 `2a2cef75fa16ec893960118dd70844c1251cb973` 恢复。

### Aurora 崩溃语义与恢复

新运行时不会接管旧代理 profile 的节点。升级前，使用旧控制面暂停并排空确切归属的 namespace，处理全部终态回传，再通过原有生命周期移除节点、sidecar 和内部网络。任何步骤失败时保留数据库与注册表恢复输入。随后同步更新私有 descriptor/config 和 API 镜像变量，以统一镜像创建新节点。本次源码变更不执行任何线上迁移。

- 注册密钥只存在于 Fleet 进程的交接表中。协调器在节点 bootstrap 前崩溃即丢失，节点失败，Aurora 在其 5 分钟 TTL 后重新 arm。密钥绝不以明文写入 SQL，也绝不自动重试。
- 回收器在节点空闲 15 分钟后停止它，在超过 8 小时后排空它，并删除其 Fleet 节点。节点删除是永久且有序的，在仍有排队工作或终态回传未解决时拒绝执行。
- 删除工作区会把 Fleet 节点行交给 Fleet 生命周期协调器，而不是删除一行 API 事务无法清理其容器和卷的记录。

## 安全与恢复

Fleet 进程持有 Docker socket，这是高权限能力。它只绑定回环，绝不能对外暴露。节点容器不会获得 Docker socket，不以 privileged 运行，不使用 host 网络或 PID 命名空间，并以非 root（`10001:10001`）运行，使用 `cap_drop: ALL` 和 `no-new-privileges`。

默认值为 2 CPU、4 GiB 内存、256 个进程、每节点并发 1 次运行，每个配置用户最多 2 个节点。

删除是永久的，并且有顺序：

- `delete` 会移除节点容器及其两个卷（data 和 secrets）。data 最后移除，因此更早的删除即使结果不确定，也总会保留 data 卷用于重新取证和重试。
- 在整个命名空间 quiesce 完成之前，Fleet 会让 API 保持存活。`make down` 和 `make destroy` 会在停止 API 之前静默（quiesce）命名空间，与组件顺序无关。
- busy、unknown-health 或清理失败都会**拒绝并保留恢复输入**（容器、卷、注册表和数据库）。没有 force 路径；不要自行构造。
- queued 或 deferred 运行会阻止删除，必须先取消。对于需要先取消的活跃或排队工作，API 返回 `409 busy`；Fleet 不会静默取消排队的工作。
- pending 或 failed 的终态回传同样阻止删除，无法取证的回传会报告为 `unknown_health`。failed 终态回传在清理之前需要恢复。
- `destroy` 需要原始 SQL 完成加上当前物理所有权，先清理资源再移除数据库和注册表，失败时中止，从而保留数据库和注册表。

## 验证门

默认的 hermetic 检查无需 Docker、数据库或任何智能体 CLI 查找即可运行：

```sh
bash scripts/fleet-env.test.sh
bash scripts/dev-env.test.sh
```

Docker 集成是**可选开启**的。Go 集成检查使用 `dockerintegration` build tag，并且只有在设置 `MULTICA_RUN_DOCKER_INTEGRATION=1` 时才运行。该门必须在任何 Docker Engine 或智能体 CLI 查找之前检查，因此跳过的运行不会触碰 socket：

```sh
(cd server && MULTICA_RUN_DOCKER_INTEGRATION=1 go test -tags=dockerintegration ./internal/fleet/integration -run TestDockerNodeRoundTrip -count=1 -v)
```

浏览器 `fleet-docker` Playwright 项目只在同一个 `MULTICA_RUN_DOCKER_INTEGRATION=1` 门下启用，绝不属于默认 suite。

真实智能体烟测是独立的，需要 `MULTICA_RUN_REAL_AGENT_SMOKE=1` 和具名的 `agentintegration` 测试 `TestAuroraSandboxRealProviderSmoke`：

```sh
(cd server && MULTICA_RUN_REAL_AGENT_SMOKE=1 go test -tags=agentintegration ./pkg/agent -run '^TestAuroraSandboxRealProviderSmoke$' -count=1 -v)
```

该测试已实现（`server/pkg/agent/aurora_sandbox_smoke_test.go`），但尚未获授权运行：未设置门变量时它会跳过，当前也没有供应商凭据或凭据文件，因此只记为 skipped，绝不记为通过。

被跳过的测试或"no tests to run"**不是**通过，缺失环境属于 setup pending（待配置），而不是失败的测试。只有在显式授权并具备确切的具名环境时，才运行这些可选门和真实模型检查。

## 本方案不提供的能力

- 不提供每个卷的磁盘配额。
- 不提供物理或密码学擦除保证。
- 不提供生产级多租户隔离。
- Docker 是容器运行时，不是 VM 安全边界；节点容器经过加固，但不是虚拟机。
- 不包含 AWS 部署。AWS 目标实例、region、账号和 stack overlay 需要单独且确切的授权与核实。
- 尚未运行 Aurora 的 API generation→asset→settlement 往返与浏览器 spec：它们需要 fake-capable 双契约节点镜像和已配置 Aurora 的受管 API/Fleet。真实供应商烟测仍未授权。
- 本页不声称任何可选门或真实模型运行已经执行或通过。
